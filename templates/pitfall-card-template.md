# 对策卡模板（pitfall card template）

> 每张卡 = 一次「症状 → 对策」的完整沉淀。放入 `pitfalls/<领域>.md`（每个领域一个文件），改完重跑 `python tools/build_index.py pitfalls/` 再生总索引。

## 卡结构（逐字段说明）

```markdown
## <症状式标题：写成"遇到什么现象"，不写成"某某功能介绍">

- **标签**: `<领域>/<子主题>/<可搜关键词……>`（斜杠分层，供 Grep 命中）
- **症状**: 具体现象 + 用户侧感知（"AI 忘事"这类表象要写清楚）。
- **根因**: （可选，能查到就写）技术层面的为什么。
- **对策**: 可复制执行的步骤，含精确命令/参数/路径。别人照着做就能解决。
- **为什么**: 对策背后的原理，防止未来环境变化时误删。
- **来源**: 链接/视频/官方文档/本机实测，尽量给一手来源。
- **状态**: 三态之一（见下）。
```

## 三态生命周期（对齐能力冷库状态机的简化版）

| 状态 | 含义 | 流转 |
|---|---|---|
| ⏳ 待验证 | 新卡默认。对策有依据但未在本机实测 | 实测后升 ✅，或证伪降 ❌ |
| ✅ 实测通过 | 本机真实跑通过（附日期与关键证据数字） | 环境变化失效时降 ❌ 或改写后重验 |
| ❌ 不成立 | 验证失败 / 结论过时 | **保留备查或定期清理**，不删除历史 |

## 纪律

1. **症状式标题**——检索靠症状命中，不靠功能名。
2. **对策必须可复制**——命令连参数一起给；"去官方文档看看"不算对策。
3. **参数数字只信一手来源**——官方模型卡/官方 repo，不信二手文章。
4. **过程材料不入卡**——卡是结论，不是流水账；中间产物进 `.tmp` 并在交付后清理。
5. **单一主题单开一个领域文件**——不要把不相关领域的卡塞进同一个文件。
6. **单项目一次性的坑不入公共 pitfalls**——放该项目的项目记忆「犯过的错」段。
