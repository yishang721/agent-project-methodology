# Handoff（交接文档）

写一份 markdown 交接简报，让一个**对本会话零记忆**的新 agent 读一遍就能执行。

接收方拥有完整工具（文件、shell、网络），但**零上下文**——假设它从没见过这个项目、这位用户、之前的讨论。任何"正如我们讨论过的""你刚才看的那个文件"这类指涉都是无效的。

## 快速开始（模式 A：一次性派单）

1. 给任务起一个短 kebab-case slug（`fix-auth-redirect`、`batch-xlsx-import`）。
2. 按下面模板写到交接文件（建议放项目文件夹或系统临时目录，如 Windows `%USERPROFILE%\tmp\`、Unix `/tmp/`），命名 `handoff-<YYYY-MM-DD>-<slug>.md`。日期取系统上下文里的今天，**不要猜**。
3. 告诉用户文件路径。用户会把它指给下一个 agent（例如"读 `handoff-2026-09-05-fix-auth.md` 然后执行"）。

### 模板

````markdown
# Handoff: <一句话标题>

**Written:** <YYYY-MM-DD> by <来源 agent / 用户>
**Repo / cwd:** <绝对路径>
**Branch:** <分支名，或 "none — not a git repo">

## Goal & acceptance criteria

<2–4 句：用户想要什么结果。然后是一份具体、可验证的完成条件清单。
接收方会把这份清单当合同执行。>

- [ ] <标准 1 — 可观察、可测试>
- [ ] <标准 2>
- [ ] <标准 3>

## Context & current state

<为什么这件事重要。已经做出的决定及其理由。试过但没走通的路。
相关文件给绝对路径 + 行号。PR / issue / 文档链接。
分支上哪些已提交、哪些没有。>

Key files:
- `<绝对路径/文件.ext>:<行号>` — <那里是什么，为什么重要>
- ...

## Constraints & verification

**Must not:**
- <硬约束：不许碰 X、不许破坏 Y、不许 push 到 main 等>

**Conventions to follow:**
- <仓库约定、代码风格、提交信息格式、分支流程>

**Verify by running:**
```bash
<接收方用来确认工作正确的精确命令>
```
````
## Suggested plan

可选。只有当你确实有足够上下文提出具体下一步时才写，并明确标注为**建议而非命令**——接收方读完代码后可能发现更好的路。如果只能瞎猜，整节删掉。

## 怎么写出一份好交接

接收方**没法回头问澄清问题**（能问也得多绕一轮用户）。所以全部前置：

- **绝对路径，不要相对路径。**
- **精确命令。** 把要跑的命令连参数一起贴出来。不要写"跑一下测试"。
- **说清分支。** 进行中的功能分支要写明；需要新建的要说叫什么。
- **引用原话，不要改写用户的需求。** 用户实际说的那句话比你的转述有用。
- **写进被排除的方案。** "试过 X，因为 Y 没走通"——能省下接收方重蹈覆辙。
- **明确划范围。** "修这个重定向 bug。即便周边代码看着别扭也**不要**重构"——不设围栏，接收方必然越界。

## 什么时候该写交接，什么时候直接干

**该写：**
- 用户明确要求。
- 剩余工作规格清楚，但你上下文不够 / 被长任务卡住 / 用户想在别处（另一台机器、另一个模型、异步）完成。
- 用户想在派单前先审一份书面产物。

**不该写：**
- 任务小到在本会话就能干完。
- 工作需要持续判断、无法在文档里钉死——交给新 agent 必然跑偏。
- 你自己都在猜验收标准。这种情况去问用户。

## 模式选择：一次性派单 vs 活文档协作

| | 模式 A：一次性派单（上面那套） | 模式 B：活文档协作 |
|---|---|---|
| 场景 | 把任务交给零上下文的 agent 执行完即止 | 同一事项跨对话 / 跨账号 / 跨工具**反复接续**，长期演进 |
| 文档生命周期 | 写完即冻结，接收方执行，不再回写 | 活文档，每次收尾自动更新 + 追加记录 |
| 文档位置 | 临时目录或项目文件夹 | **项目文件夹内**（跟着项目走），换账号/换工具打开同一文件夹即可接手 |
| 核心机制 | 自包含简报 + 验收清单 | 开场/收尾口令协议 + 十板块结构 + 更新记录 |

混合场景（先派单、后续变成长期项目）允许升级：模式 A 文档执行完若用户要继续，按模式 B 的结构补建活文档。

> ⚠️ 互链：新项目启动判级、活文档提纯（阈值/五步制）、坑的三级分流 → 同仓库 `skills/project-bootstrap/` 技能。本技能只管口令协议与文档结构，两技能规则冲突时以对方领域技能为准，勿在本文件复抄。

## 模式 B：活文档协作（跨对话接续）

> 核心思想（源自「交接文档驱动」工作法，作者 @吴嘉文GW，[原版提示词文档](https://my.feishu.cn/wiki/E8XNw07B6iJNEwkR6PWcCGtxnMg)）：**按文件接管，不按聊天记录接管**——所有状态以文档为准，换新对话、换账号、换 AI 工具，只要打开同一份交接文档就能无缝继续。
> **许可说明**：本节工作法遵循 **CC BY-NC**——非商用免费（须保留署名与原版链接）；商用（付费产品/商业服务/企业方案）需事先取得作者授权。详见仓库 CREDITS.md。

### 两个固定口令（写进文档，双方遵守）

用户说以下口令（或意思相近的说法）时，AI 按对应协议执行：

- **开场口令**："阅读交接文档，准备开始"（近似："读一下交接文档""看看交接文档，继续做"）
- **收尾口令**："结束对话，总结项目"（近似："总结一下""今天到这，收个尾"）

存在多份交接文档时，按用户提到的名称或最近更新的文档定位；无法确定时列出候选让用户选。

### 生成活文档

用户要求"生成交接文档""存档这个项目"时，按下面模板写到**项目文件夹内**（不放临时目录），命名 `【事项名】交接文档.md`：

- 事项名从对话内容自动取一个简短具体的名字（项目名/话题名/文档名），用户已指定过名称就直接采用。
- 文档开头标注对话类型：项目开发 / 咨询问答 / 文档制作 / 图像创作 / 混合。各类型填写侧重不同：
  - 项目开发 → 重点在规格、决策、待办
  - 咨询问答 → 重点在结论与依据、未决问题
  - 文档制作 → 重点在格式要求、版本与修改记录
  - 图像创作 → 重点在风格要求、版本与修改记录

### 活文档模板（十板块）

````markdown
〇、协作约定（此段原样保留在文档里，一字不改）
本文档用于「交接文档驱动」的跨对话协作，所有状态以本文档为准。
- 用户说"阅读交接文档，准备开始"或意思相近的说法 → 按开场协议执行
- 用户说"对话结束，总结项目"或意思相近的说法 → 按收尾协议执行
- 多份交接文档按名称或最近更新定位；无法确定时列出候选让用户选。
- 开场协议：①用3-5条汇报对目标/进度/关键结论的理解 ②列出下一步待办并给建议 ③有明确风险才单列，没有则整段省略 ④以"你想先开始做什么？"结尾
- 收尾协议：①把一~八板块更新到最新状态 ②把本次对话中用户新告知的信息、新提出的要求或方法，追加到「九、对话信息记录」 ③在「十、更新记录」末尾追加：第N次对话（N=现有记录条数+1）、当前日期时间、本次改动 ④不删除、不覆盖历史记录，未决项已解决移入已确认、未解决保留标★ ⑤输出确认"已更新交接文档，新增第N次记录"

一、背景与目标（为什么做 / 想达成什么 / 范围边界）
二、关键规格与结论（按类型填：项目→规格参数；咨询→核心结论及依据；文档→格式与内容要求含字体配色结构页数等具体参数）
三、已做决策（选定方案及理由 / 否决备选及原因）
四、待确认未决项（一律标★，不要替用户补答案）
五、关键数字与口径（数值 / 来源：实测或推算 / 备注；没有写"无"）
六、产出物清单（文件/结论/图表：路径或位置 → 版本 → 用途）
七、下一步待办（咨询类填：可跟进的问题）
八、风险与问题（没有写"暂无"）
九、对话信息记录（每次对话追加，不覆盖，注明来源对话的时间）：
  9.1 用户告知的相关信息——精简概括，只保留与该事项相关的重要信息
  9.2 用户提出的要求或方法——详细记录（要求内容、参数、处理方法、修改意见，不得简化）
十、更新记录（第 1 次对话 + 今天日期时间 + 改动：创建文档，沉淀本次对话内容）
````

**生成纪律：** 只写对话中真实确认过的内容，禁止编造数字，样本不足写"暂无推算"；未决项必须标★，不自设假设。

### 开场协议（收到开场口令时执行）

1. 读项目文件夹内的交接文档（多份时按名称/最近更新定位，不确定就问）。
2. 用 3–5 条汇报对目标 / 进度 / 关键结论的理解。
3. 列出下一步待办并给建议。
4. 有明确风险才单列，没有则整段省略。
5. 以"你想先开始做什么？"结尾。
6. **先读再动手**——确认理解无误、用户点头之前，不改任何文件。

### 收尾协议（收到收尾口令时执行）

1. 把一~八板块更新到最新状态。
2. 本次对话中用户新告知的信息、新提出的要求/方法，追加到「九、对话信息记录」（告知的信息精简概括；要求和方法详细记录，不得简化）。
3. 「十、更新记录」末尾追加：第 N 次对话（N=现有记录条数+1）、当前日期时间、本次改动。
4. 不删除、不覆盖历史记录；未决项已解决移入已确认，未解决保留标★。
5. 输出确认："已更新交接文档，新增第 N 次记录"。

## 反模式

- **成功标准含糊。** "让它能跑""清理一下"等于没给合同。写不出检查清单，就还不配写交接——先澄清。
- **泄漏会话状态。** "如上所述""你之前看过的那个文件"对新 agent 全是噪音。每条引用必须自包含。
- **把计划定死。** 接收方会读真实代码，可能看出更好的路。除非用户已明确选定方案，否则只建议不命令。
- **把密钥写进文件。** 交接文档可能被转发。用环境变量名或路径指代，不要粘贴明文。
- **忘了告诉用户路径。** 这个技能的产出就是文件路径——必须清楚地报出来。
- **活文档覆盖历史。** 模式 B 收尾更新时不许删除或改写既有记录，只允许追加与状态迁移（未决→已确认）；历史被覆盖等于丢账。
- **活文档放临时目录。** 模式 B 文档必须放项目文件夹随项目走——放临时目录等于换机器就失联。

## 操作者约定（Operator conventions · 按你自己的协议改写此段）

以下为本仓库作者实践中的通用守则，采用者可按自身工作流改写：

- **破坏性操作必须留给人类。** 删除 / 覆盖 / 终止进程 / 对外发送 / 付费，写进 `Must not`，要求接收方先向用户显式确认；泛化的"继续 / 好的"不视为批准，建议一次性确认词。
- **验证命令必须是你真跑过的。** 不许写没执行过的命令当验收标准。
- **批量任务建议样品审批。** 先 2~5 个样品给用户确认再铺开。
- **领域事实以权威资料为唯一来源。** 接收方不得自创或改写领域专有名词。
- **产出物路径。** 让接收方把产物放到用户指定目录，不要散落临时目录。
- **未决项标★。** 交接文档里用户没拍板的事项一律标★留给用户，接收方不得自设假设补答案。
